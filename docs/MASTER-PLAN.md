# Master plan: one accessibility toolkit

This is the working plan for turning a dozen accessibility repos into one tool developers use on every pull request. It is the single source of truth for that cross-repo work. Engine internals keep their own detail in `docs/implementation-roadmap.md`; this plan links to it rather than repeating it.

## How to use this file

- **Start a session:** open a Claude Code session on `accessibility-evidence-engine` and say _"continue the master plan"_. `CLAUDE.md` points here, so a fresh chat picks up the context without any earlier conversation.
- **One step per session.** Each step is sized for one sitting and has a "done when" line.
- **Tick the box in the same PR that does the work.** The file is then always true, and git history is the log.
- **Decisions go in the Decisions log below**, not in chat. Chat is lost; this file is not.
- **Current focus: the tool works for its owner.** Publishing (npm, PyPI), public showcases and the portfolio map wait in [Later](#later-parked) until it does.

## Goal

A developer opens a PR. CI runs their Playwright journeys with the engine attached, then:

1. **Deterministic checks fail the build** on real violations (axe plus AEE's own judges).
2. **AI suggests the fix** for each violation, using a screenshot of the section and the page context. This is advisory, labelled as AI, and never fails the build.
3. **Each finding links to the pattern** that explains it (a11y-skills).

```mermaid
flowchart LR
  PR["👩‍💻 Developer opens a PR"] --> CI["CI runs Playwright journeys<br/>with the engine attached"]
  CI --> DET{"1 · Deterministic checks<br/>axe + AEE judges"}
  DET -- "violation" --> RED["❌ Build fails"]
  DET -- "clean" --> GREEN["✅ Build passes"]
  CI --> AI["2 · 🤖 AI suggests the fix<br/>advisory, never fails the build"]
  RED --> COMMENT["💬 One PR comment"]
  AI --> COMMENT
  COMMENT --> PAT["3 · 📘 Link to the a11y-skills pattern"]
```

The first rules covered are unlabeled buttons, unlabeled links, missing alt text, missing form labels and empty headings. This is the exit test of Milestone 3 in `docs/implementation-roadmap.md`, widened from one rule to five.

**Outcome:** Test pages with known answers catch any missed or false finding, and the report never contradicts itself.

- [x] **2.3** Sweep findings in the report: `aee run` sweeps each journey's start page, pressing controls only when the journey's `allowedActions` include `activate-page-controls`. ## Decisions log

Newest first. One line each: date, decision, why.

- 2026-09-28 — AI in CI runs on a free model on the runner, not a provider key: `ai-provider: local` starts Ollama (v0.34.4, downloaded from its GitHub release and checked against its SHA-256) with the local provider's default model, `gemma4:e4b`, so no key, account or bill is needed and page evidence never leaves the runner. `scripts/start-local-model.sh` does it for the Action and the Pages deploy alike. It skips Ollama's GPU libraries (2 GB of 2.2 GB; a runner has no GPU), sets an 8,192-token window (the specialist prompt is about 3,000 tokens and the CPU default is 4,096), keeps the model loaded for the whole run, and turns Ollama's cloud models off, so no model name can send evidence elsewhere. Both workflows switch to Claude by themselves once an `ANTHROPIC_API_KEY` secret exists. The Action's default stays `stub`. The self-test job pays for the download on every pull request, although the fixed page passes and asks the model nothing, so that a change that breaks the page gets a suggestion too. CI's own shots stay on the stub; the Pages deploy names the model, and the shots test fails if the AI card would show anything but a suggestion. M4 closes, so the homepage gets both cards 4.4 promised: the AI suggestion, cropped from the report's button fix, and the pull-request comment, rendered from the same run's `aee-pr-comment.md` with `marked` (a new dev dependency) and styled like a GitHub comment, with its first fix opened. Why: the owner chose to postpone a paid key, and a model on the runner proves the same done-when at no cost.
- 2026-09-28 — The self-test, `.github/workflows/accessibility.yml`, serves the pull request's own copy of `site/` and runs the Action (`uses: ./`) on the lab's fixed page with `examples/test-lab/scenario.yml`, an approved scenario with the lab tests' sweep permissions and reader walk; a unit test keeps it approved as written. It runs on the fixed page, not the issues page, which is always red: a change that breaks the fixed page is the regression to catch. It fails on `incomplete` rather than the Action's default `blocking`: in a rehearsal where the page did not load, the verdict was "not decided", which `blocking` lets through. The Action now pins `actions/setup-node` and `actions/upload-artifact` by commit, like every workflow here, and uses Node 24 like CI. The done-when ran on the step's own pull request: the workflow alone was green with "nothing blocks release"; a demo commit that added a nameless icon button turned the job red and edited the same comment (created 06:59, edited 07:00) to "release blocked, 1 fix needed" with the buttons pattern link; its revert made the job green again. The homepage gets a PR-comment feature card when M4 closes, with 4.5's AI card; until then the "In progress · M4" card stands for it. Why: the Action checks itself on every change, the way a team would use it.
- 2026-09-28 — The Action (`action.yml`, composite) sets up Node 22, installs and builds AEE from its own checkout (nothing is published yet), runs the `run` input (a `.yml`/`.yaml` scenario through `aee run`, anything else as a shell command), keeps the reports as the `aee-reports` artifact, and runs `aee comment`.
