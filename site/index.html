One interaction, evidence from every lane

See exactly how an accessibility result is produced

A deterministic orchestrator runs the same scenario through focused evidence workers. AI is optional and receives only questions that require contextual judgment.

Read the graph as six text steps
  1. Define: version the journey, actions, policy, and tools.
  2. Isolate: run pointer, keyboard, virtual-reader, and optional real-AT drivers in separate browser contexts.
  3. Capture: record a synchronized state before and after every meaningful action using passive visual, DOM, AOM, focus, axe, transcript, and video observers.
  4. Correlate: join immutable artifacts into one evidence graph.
  5. Analyze: run deterministic rules first, route only allowlisted contextual questions to labeled AI, then verify across all evidence.
  6. Report: publish one linked HTML, JSON, and Markdown report; any fix is isolated and must pass a verified rerun.

This is the target evidence architecture. Colors distinguish deterministic or available work from optional, contextual, or planned integrations. Read the artifact contract and Mermaid source on GitHub.

Deterministic first, AI by exception

How findings map to evidence and fixes

This table is generated from the versioned JSON registry. “Partial” and “Planned” describe implementation status, not accessibility conformance.

Detection, AI scope, and verification requirements by accessibility issue
Issue and mapping Deterministic detection AI contribution Verification
Missing or unsuitable accessible name Partial WCAG 4.1.2, axe-core button-name, axe-core link-name, axe-core label
  • Run pinned axe-core rules at each meaningful checkpoint.
  • Compute the accessible name and compare it with the rendered role and visible text.
AI-assistedSuggest a concise, context-specific name when deterministic checks can prove a name problem but cannot author the wording.
  • Rerun the same journey and prove the computed name is non-empty and unique enough for the task.
  • Match visible purpose, DOM, accessibility tree, and screen-reader output.
  • Confirm keyboard activation and resulting user outcome are unchanged.
Image purpose and text alternative Planned WCAG 1.1.1, axe-core image-alt
  • Identify rendered non-text content and its exposed alternative or hidden state.
  • Flag mechanically provable missing alternatives and role conflicts.
 AI-assistedClassify an image as decorative, informative, functional, or complex and draft text only when page context is required.
  • Confirm the rendered image, nearby content, DOM treatment, accessibility tree, and spoken output express the same purpose.
  • For decorative images, verify they are absent from the accessibility tree and spoken output.
Visual and semantic heading structure Partial WCAG 1.3.1, axe-core empty-heading
  • Extract the complete semantic heading outline and structural relationships.
  • Record visual typography and grouping signals without deciding meaning.
AI-assistedCompare the full visual hierarchy with the full DOM and accessibility-tree outline when the intended relationships require contextual judgment.
  • Re-extract the full outline after the fix.
  • Confirm visual grouping, DOM hierarchy, accessibility tree, and screen-reader heading navigation agree.
Text and component color contrast Partial WCAG 1.4.3, WCAG 1.4.11
  • Use axe-core where foreground and background colors can be determined.
  • Calculate WCAG contrast ratios from resolved colors; never let a model estimate the ratio.
  • Select the closest passing supplied design token using deterministic color-distance and contrast calculations.
AI-assistedLocate complex rendered foreground and background regions or explain brand intent when deterministic extraction is inconclusive.
  • Recompute the exact contrast ratio from the final rendered colors.
  • Verify default, hover, focus, active, disabled, and error states that apply to the component.
Keyboard operation and activation Partial WCAG 2.1.1
  • Drive Tab, Shift+Tab, Enter, Space, arrows, Escape, and role-specific keys through the active keyboard lane.
  • Record document.activeElement, deep active element, aria-activedescendant, visible focus, and accessibility-tree focus after every meaningful action.
  • Compare the observed outcome with the scenario's authorized expected outcome.
Deterministic onlyKeyboard operability and focus movement are verified from recorded behavior, not inferred by AI.
  • Repeat the same role-aware key sequence in an isolated active lane.
  • Confirm focus moves only when required and the user outcome matches pointer activation.
  • Require explicit authorization before destructive or financial actions.
Hover and keyboard-focus equivalence Planned WCAG 1.4.13
  • Run hover and keyboard paths in separate active browser contexts.
  • Capture synchronized before and after evidence for hover, focus, Enter, and Space when appropriate to the role.
  • Compare available user outcomes rather than requiring identical implementation events.
Deterministic onlyEquivalent behavior is decided from traces and outcomes; AI does not substitute for exercising both paths.
  • Verify hover content is dismissible, hoverable, and persistent where WCAG requires it.
  • Verify the equivalent information or control is reachable and usable by keyboard and represented consistently to the screen reader.
Focus management after interface changes Partial WCAG 2.4.3, WCAG 4.1.3
  • Record focus and aria-activedescendant before and after every meaningful action.
  • Detect loss of focus, hidden focused elements, and focus outside an opened modal.
  • Record live-region and screen-reader output separately from focus movement.
Deterministic onlyFocus movement and announcements are observable state. AI may explain evidence later but cannot decide or cause the movement.
  • Confirm only the active input driver moves focus.
  • Do not both move focus and announce the same update unless the interaction pattern requires both.
  • Match focus, visible context, DOM, accessibility tree, and spoken output after the action.

Example 1 of 6 · Contextual AI review

Give an icon-only button a useful name

axe detects the missing name. AEE uses the icon, project heading, and destination copy to suggest the product-specific label “Delete Project Alpha.”

Example 2 of 6 · Full-page hierarchy

Make the semantic outline match the visual structure

axe passes the valid heading sequence. AEE sees that “Settings” visually groups three sections and proposes the missing parent relationship for review.

Example 3 of 6 · Behavioral evidence

Move focus into an opened modal

The same Playwright interaction runs twice. Before, focus remains on the trigger behind the dialog. After the fix, focus lands on Cancel inside it.

Example 4 of 6 · Palette-aware repair

Choose the closest passing color already in the palette

The contrast failure is objective. AEE measures the existing design tokens and proposes the perceptually closest one that passes—without inventing a new color.

Example 5 of 6 · Interaction equivalence

Expose hover information to keyboard users

AEE runs the pointer and keyboard paths from the same reset state, then compares their observable outcomes instead of assuming equivalent CSS means equivalent use.

Example 6 of 6 · Time-based verification

Verify that a Pause control really stops animation

AEE samples after the stop request twice. That distinguishes lasting stillness from a single screenshot that merely caught the animation between frames.

Trust requires boundaries

What a passing report does—and does not—mean

AEE can support

  • Repeatable investigation around selected interactions
  • Evidence-linked triage and release-policy decisions
  • Explicit unknown and unsupported results

AEE cannot certify

  • Complete WCAG conformance
  • All assistive-technology experiences
  • That captured artifacts are safe to share without review
