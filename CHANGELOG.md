# Changelog

All notable changes to Accessibility Evidence Engine are documented here. The project follows [Semantic Versioning](https://semver.org/) while its public APIs remain experimental.

## [Unreleased]

### Fixed

- The site renders its markdown with `marked` instead of its own regexes (audit C12). Bold or link syntax inside a code span, such as `` `**name**` ``, now shows as written instead of turning into bold text or a link inside the code. Raw HTML in the text is still escaped and shown as written. On the roadmap, step 7.3's link to the Page view spec, which showed as raw `[spec](qa-designer-view.md)`, is now a link to that doc on GitHub: a relative link resolves against the file its text comes from. The committed homepage is unchanged.
- A plan's digest is the same on every machine (audit C7). AEE sorted the plan's actions and allowed origins with `localeCompare`, which follows the language the machine is set to, before hashing it, so a plan approved on one machine could read `DIGEST-MISMATCH` on another and refuse to run: on a machine set to Estonian, which sorts "z" between "s" and "t", a journey allowing `zoom-page` and `tab-to-page-end` got a different digest than in English. The digest is now the SHA-256 of the plan's RFC 8785 canonical JSON, from `canonicalize` 5.1.0, and the lists are sorted by UTF-16 code unit, RFC 8785's order. A digest approved on an English machine stays valid, including both examples', unless its allowed origins put a port beside a dot (`http://x:8080` and `http://x.test`). An approval made with AEE 0.8.0 or earlier on a machine whose language sorted the plan differently stops matching once; `aee plan` and `aee run` now say that this, or a change to the scenario, is why, and to review the plan and approve it again.
- AEE reads axe's results from axe's own structured data instead of its English sentences (audit A9). Verdicts are unchanged: what passes, fails or blocks release is the same as before.
  - **Severity follows axe's impact.** Every axe violation was labelled "high". Each finding now takes axe's own impact: critical stays `critical`, serious is `high`, moderate is `medium` and minor is `low` (`info` stays unused, as axe has no lower level). A rule axe gives no impact keeps `high`. The axe judgment itself stays `high` and still fails on any WCAG violation, so the release gate is unchanged. The fix card's badge shows the new label, and a critical finding is now P0 in the fix plan. The axe evidence record lists each blocking rule's impact in a new `meta.violationImpacts`.
  - **Contrast numbers come from axe's `check.data`.** The required ratio, the colours and the measured ratio were read back out of axe's message with regular expressions (`Expected contrast ratio of 4.5:1`, `foreground color: …`), which break as soon as axe runs in another language. They now come from axe's `fgColor`, `bgColor`, `contrastRatio`, `expectedContrastRatio`, `fontSize` and `fontWeight`, and each affected text in the report gains a `contrast` field with them and with who measured it (`axe`, or `screenshot` when AEE measured the pixels). The proposed passing colour is now checked against every measured background, each at its own text's required ratio, not only the first three texts at the first ratio found.
  - **AEE's own pixel measurement stays AEE's.** When AEE settled a contrast axe could not decide over a gradient or image, it wrote the result into axe's message in axe's wording, for the report to read back with a regex. axe's message is now left as axe wrote it, the numbers stay in `aeeContrast`, and the report says it in AEE's words: "Measured from the screenshot: #ffffff has 2.1:1 to 2.45:1 against what is behind it (#b0b0b0 to #a0a0a0), where 4.5:1 is needed."
  - **An element inside a shadow root keeps its full path.** axe's target `[["#host", "button"]]` was flattened to `"#host,button"`, a CSS list that matches the host. The report now writes it `#host >>> button` (frames still joined by `→`) and keeps axe's whole target array in each affected element's new `target` field. On the page screenshot the element is located by walking into the shadow root, so its crop shows the element itself instead of the whole host. The page around an element, captured for an AI specialist, is now captured only for an element in the top document's own tree: for one inside a frame or a shadow root it described the frame or the host, a different element.
- AI suggestions from OpenAI (`AEE_LLM_PROVIDER=openai`) work. AEE called OpenAI's Responses API with a hand-written `fetch` and read `output_text` from the reply, but that field is not in what the API sends: the official SDK adds it on the client, by joining the message's text parts. So every OpenAI request failed with "OpenAI Responses output did not include output_text.", and the fix card showed no AI suggestion. AEE's unit tests faked a reply that had the field, which hid it; they now fake the reply as the API sends it. The OpenAI and local providers (`AEE_LLM_PROVIDER=local`: Ollama, LM Studio, llama.cpp, vLLM) now call the official `openai` SDK 7.28.0, the local one pointed at `AEE_LLM_BASE_URL`, and read the answer with the SDK's structured-output parsing (`responses.parse`, `chat.completions.parse`) against the specialist's strict JSON Schema. An OpenAI refusal is an error that names it, never a suggestion, as Claude's is, and a failed OpenAI request is retried twice, the SDK's default. The local client is given every OpenAI credential itself, so an `OPENAI_API_KEY`, admin key, organization or project set for OpenAI is never sent to the local server; with no `AEE_LLM_API_KEY` it sends the placeholder key `local`, which local runtimes ignore, and it still does not retry. An AI answer is still labelled "AI suggestion" and never passes or fails anything. `OpenAiResponsesModelProviderOptions.baseUrl` now defaults to the SDK's `OPENAI_BASE_URL`, else OpenAI's API. A local base URL ending in more than one `/` is no longer trimmed: the SDK drops one.
- The virtual reader's "announced without a name" follows WAI-ARIA 1.2's "Accessible Name Required", taken from `aria-query` 5.3.2 (which follows the ARIA 1.2 Recommendation), instead of a hand-written list. An unnamed progress bar, meter, tab panel, tooltip, radio group, tree, tree item, tree grid, grid, table, column or row header, application or graphics document is now reported in the Virtual reader status row and marked "No name" on the Page view; before, none of them was. An empty tab is no longer reported: ARIA 1.2 names a tab from its content and does not require a name. axe's `aria-tab-name` rule (WCAG 4.1.2) still fails an unnamed tab in the Semantics row, and the reader now catches a native `<progress>` with no name, which axe's `aria-progressbar-name` does not check (it selects only `role="progressbar"`). Chrome's `image` role counts as ARIA's `img`, so an unnamed image still does, as do a heading, dialog and alert dialog. An unnamed `role="region"` or `role="form"` is still not reported, because Chrome exposes it as a generic container, not a region or form (Core-AAM), so the reader never reads one.
- The keyboard and pointer sweep no longer stops its Tab walk at a frame with two or more controls of its own, and so no longer says the page's controls after that frame work "with a mouse only". The walk knew where focus was only by the top document's active element, which is the frame's `<iframe>` element for every control inside the frame. The second Tab inside the frame looked like focus coming back to a stop already reached, so the walk ended there, and every control after the frame was reported as `pointer-only`. A component's shadow host with two or more controls inside it ended the walk the same way. The sweep now follows focus into shadow roots and into each frame it reads, cross-site frames included, through `focusPath`, which the focus observer and the reader already use, and ends the walk only when focus comes back to an element it has already been on. The frame's element, or the component's host, is still one Tab stop. Inside a frame the sweep does not read (outside the allowed origins, or showing Chrome's error page), Tab moves where the sweep cannot see while focus stays on the frame's element, so the walk goes on until focus leaves the frame. That frame's stop still says "Not checked" and why. `maxTabStops` counts each Tab press, inside a frame too.
- The keyboard and pointer sweep no longer sweeps a site outside the allowed origins when its start page redirects there. Playwright's `route` handler sees only the first URL of a redirect, so a start address that answered 302 to another origin got past the sweep's navigation guard: the sweep tabbed through and pressed controls on the other site and recorded the lane `completed`, with that site's results as the page's. The sweep now checks where the page landed each time it loads it, before reading or pressing anything, and records the lane `blocked`, as the reader, comparison and start-page lanes do. The sweep lane also leaves evidence when its browser cannot open its pages: it opened its two browser contexts before anything that writes its record, so a browser that crashed, disconnected or ran out of memory there left no manifest and no `keyboard-pointer-sweep.json`; it now writes both, marking the lane `failed`.
- The keyboard and pointer sweep reads nothing on a page outside the allowed origins that a pressed control reaches, and says where the press went instead. A press that went to an address on the site that then redirected to another origin passed the navigation guard, since Playwright calls a `route` handler only for the first URL of a redirect. The sweep then read the other site's page to compare the click with Enter, and could blame the site under test for a difference only the other site made; the lane said `completed` and listed nothing in `blockedNavigations`. Playwright cannot stop that request, since the browser follows a redirect before the guard is asked, so the sweep now checks where the page is before and after each read and refuses a page outside the allowed origins. A press that sets out for another origin, whether the guard stops it or a redirect takes it there, is compared by its address alone: a control that a click takes off-site and Enter does not is still reported as `activation-differs`, and its focus and messages are not read. The lane lists the redirect's address in `blockedNavigations`. A press the guard stopped was read before too, on Chrome's error page for the stopped load.
- The keyboard and pointer sweep reads nothing in a frame that a redirect takes outside the allowed origins. A frame whose address on the site answered 302 to another origin got past the navigation guard, since Playwright calls a `route` handler only for the first URL of a redirect, and the sweep's heading check read every frame: the other site's text could come back as a `looks-like-heading` finding of the page, while `blockedNavigations` listed the same address as blocked. The sweep now leaves out a frame outside the allowed origins, and every frame inside it, and lists each in the lane's `framesNotRead` with why, so a scenario report says that frame's content was not checked; a frame showing Chrome's error page is left out the same way. The frame element on the page is still swept, so Tab still reaches it and reads its name, and the page's own frames are read as before. The browser has still loaded and drawn that frame, so the lane's full-page screenshot and each Tab stop's focus crop cover it with Playwright's screenshot `mask`, a solid pink box; without it, the other site's page showed in them. The video still shows it, since Playwright's `recordVideo` has no mask. A Tab stop that is such a frame no longer says "No visible focus": with both of its pictures covered, the focus-visible check compared two pink boxes and recorded `focusVisible: false`, a failure for a frame the sweep never checked. The stop now has no `focusVisible`, and its new `notChecked` gives the frame's reason, naming the site; the report's Focus layer says "Not checked" with that reason and keeps the stop's close-up.
- A press whose page on the site does not load no longer stops the keyboard and pointer sweep. When the server dropped the connection, Chrome showed its own error page, and the sweep stopped there with "blocked origin null", recording the whole lane `blocked` and keeping none of its other results; before that, it read Chrome's error page as the site's and said nothing about the failure. The sweep now reads nothing on Chrome's error page, compares the click with the key press by where each set out for, so a control a click takes there and Enter does not is still `activation-differs`, and sweeps on. The lane lists each such page in `failedNavigations`, with the control pressed and Chrome's reason, and a scenario report says it as a diagnostic.
- A journey's start-page lane reads nothing inside a frame of the start page whose page is outside the allowed origins, and says the frame was not checked instead. A frame whose address redirected to another origin got past the navigation guard, since Playwright calls a `route` handler only for the first URL of a redirect; the checkpoint then read the other site's page into the start page's accessibility tree, element map, axe result, screenshots and report, and listed nothing in `blockedNavigations`. Now the frame's `<iframe>` element is still checked on the start page, but nothing inside it is read: the accessibility tree lists it under `framesNotRead` with the reason, axe leaves the frame out with its element (excluding only what is inside a frame still loads axe into its page, and `@axe-core/playwright` does not pass axe's `iframes: false` run option on), the screenshots cover it with Playwright's `mask`, and the lane lists the redirect's address in `blockedNavigations`. Its name comes from Chrome's accessibility tree, since axe's `frame-title` rule no longer sees it: a frame with no name fails `frame-title`, and a named one makes the axe judgment `unknown`, saying axe did not check the frame, with its address and the site to add to the allowed origins to check it, so the page is not decided. A frame showing Chrome's error page, as one the guard stopped does, is left out the same way. The frames are left out by `framesInsideOrigins`, which the keyboard and pointer sweep uses too. A start page that itself redirects off the allowed origins is still `blocked`. Every lane that stops at a page outside the allowed origins now names that page's address in its error (with no credentials, query values or fragment), not only its origin.
- A journey's start-page lane leaves evidence when it fails before its page opens. It opened its browser context before anything that writes a manifest, so a browser that crashed, disconnected or ran out of memory there, or a start page that failed to load or redirected off the allowed origins, left no manifest for the lane at all; the report said "incomplete" only from its lane count and an error line. The lane now writes its manifest marking it `failed`, or `blocked` when it stopped at a page outside the allowed origins, as the reader and comparison lanes do. A 302 redirect to another origin is caught after the load: Playwright's `route` handler sees only the first URL of a redirect.
- The site's logo link is named by its visible words, "Accessibility Evidence Engine", instead of an `aria-label` that replaced them ("Accessibility Evidence Engine home"). axe 4.14 runs `label-content-name-mismatch` (WCAG 2.5.3, Label in Name) by default and flagged it on the homepage, How it works and the real screen readers page.

- The Action's free local model (`ai-provider: local`) no longer fails the job when Ollama's registry is briefly unavailable. Ollama asks the registry for the model's manifest once, without retrying, and answers HTTP 500 to any registry error, so a passing 503 failed the "Start the local model" step with curl's exit code 22, and AEE ran no assessments; a re-run usually passed. `scripts/start-local-model.sh` now asks again with curl's own `--retry`, which counts a 500 as transient: 9 tries, 1 to 128 seconds apart, about four minutes in all, and Ollama resumes a retried download where it stopped. A model still missing after that fails the step with a message saying it could not be downloaded, above Ollama's own answers.
- The suggested fix for a press that got no response names what counts as one, instead of "an observable response such as DOM, focus, or network activity". A change to the HTML alone has not counted since the judges began reading Chrome's accessibility tree, so that advice sent developers after a change the judge would still fail. The keyboard and change-response judges now say: change the control's accessibility state (checked, expanded, pressed, selected, value or name) or that of what it names with `aria-controls`, move focus to what it opens (for a click or submit, not only onto the control itself), announce the result in a live region ([WCAG 4.1.3 Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)), or make a network request; a markup change alone does not count. This is the list in [What counts as a response](docs/playwright-integration.md#what-counts-as-a-response). Verdicts are unchanged. Keyboard judge 0.4.1, change-response judge 0.4.1.
- `aee run` checks every journey's start page with axe. A journey with no `virtualScreenReaderCommands` or `interactionComparisons` ran no axe at all, though its plan listed "Run the pinned WCAG rule selection", and its report said "nothing blocks release in the tested scope" without checking a rule. The start page is now checkpointed once before anything acts on it, as its own lane (`<journey>-start-page`, driver `page-load`), and a run with no axe result can no longer pass: it reads "not decided, some evidence is missing or needs a person". Scenarios that had reader commands or comparisons gain this lane too, so their reports count one more lane and one more checkpoint: the Page tab shows the start page as it loaded, with its axe issues, as a picture of its own beside the reader's, and axe findings now come before the keyboard sweep's, in the order the plan runs them.

### Changed

- `aee` reads its command line with Node's built-in `util.parseArgs` instead of three hand-written parsers (audit C5). Each command's options are defined once, and both its usage line and the parsing are made from that one definition, so they cannot drift apart: `aee` on its own listed `aee comment … [--post]` without `--images`. Every command line that worked before is read as before, with one exception for a value that starts with a dash (below). **Behaviour change: an option or argument a command does not know is now an error that names it,** where before some were ignored without a word. `aee plan scenario.yml --jsno` printed the text plan as if the misspelt `--json` were not there; `aee run config.json --ci` ran a JSON fixture config without `--ci`, so the job could never fail on it; `aee comment reports -p` read `-p` as a folder, so a misspelt `--post` posted nothing; and `aee plan a.yml b.yml` planned `a.yml` alone. Each now stops with exit code 1 and an error such as `aee plan: Unknown option '--jsno'.`, followed by the command's usage line. What else is new, as in other command-line tools:
  - `--option=value` works: `aee run scenario.yml --output=reports` and `aee comment reports --fail-on=never` were refused as unknown options.
  - `--` ends the options, so what follows is read as a path even when it starts with a dash: `aee comment -- -reports`. `aee comment --` read `--` as an unknown option.
  - An option may come before the path, as in `aee plan --json scenario.yml`, which was refused.
  - **A value that starts with a dash is given with `=`**, as in `aee fix … --start=--watch`, which could not be given at all. `--output -reports` was read as the folder `-reports`; it is now refused as ambiguous, with the `--output=-reports` form to use instead, since a value like that is more often a slip than a folder name. A path that starts with a dash goes after `--`.
  - A refused command line says which command it was and ends with that command's usage line. Messages for an option given twice, a missing value or a missing argument now come from Node: `--accept needs a value` reads `aee fix: Option '--accept <value>' argument missing`. An option given twice still keeps its last value, and `--accept` still adds one fix each time. An empty value, such as `--output ""`, is refused for every option.

- The MCP server's `findings` and `run` tools give a coding agent every finding in full (audit C3). They returned only the pull-request comment, which lists five elements per finding, at most 60,000 characters, and no checkpoints, evidence paths, contrast readings or verification steps, so an agent asked to fix a contrast failure on six elements saw five. Both tools now return MCP structured content, `{ verdict, assessments: [{ folder, report }] }`, where each `report` is the assessment's whole `aee-report.json` and `folder` is where its evidence paths start, and declare it with an output schema whose report part is AEE's own integrated-report schema, so a client can check it. The comment stays as the text, for clients that read only text. A report that does not match the schema is a tool error naming the field, not a partial answer. `@aee/schemas` gains `bundledSchema(name)`, a schema with every AEE schema it refers to embedded under `$defs` (JSON Schema 2020-12 bundling), for readers without AEE's other schema files. `@aee/cli`'s `buildPullRequestComment` returns the assessments it read, `assessments: [{ report, dir }]`, in place of their count, `reports`.
- The MCP server's `explain` reads the a11y-skills index as markdown, with the `marked` lexer, and finds a pattern's front matter with YAML's own parser, instead of regular expressions (audit C13). The regex missed two rows of the real index: "Tab order jumps around", which opens focus-management and landmarks, and "axe: ARIA attribute not allowed / invalid role", which says "the widget's own file, then accessibility". So "tab order jumps around" was answered with the tabs pattern, and "ARIA attribute not allowed" with listbox. They now get focus-management (also consider landmarks) and accessibility. Any valid way of writing the table now routes the same: Windows line endings, rows without outer pipes, aligned columns, a `./` link or a link with a title. Front matter is now taken off a pattern with Windows line endings too. `@aee/mcp` now depends on `marked` 18.0.14 and `yaml` 2.9.1.
- AEE's schema validator runs Ajv in strict mode, so a mistake in one of AEE's own schemas fails when the schema compiles instead of being ignored (audit C2, first part). It ran with `strict: false`, which hid three such mistakes: `evidence-record.schema.json` gave the accessibility-tree record's and the reader record's `meta` its `properties` with no `"type": "object"`, and `virtual-screen-reader-lane.schema.json` required a completed lane's `steps` to have an item with `minItems` and no `"type": "array"`. Each now names its type. They let no wrong data through, since the property's top-level definition already gave the type, but strict mode treats a keyword with no type as a likely mistake. Ajv's `strictSchema` (unknown keywords and formats) and `strictNumbers` are on by default; `strictTypes` and `strictTuples`, which only log by default, now fail the compile too. `allowUnionTypes` lets `type` list several types, which JSON Schema allows and three properties use (a state change's `before` and `after`, a transcript item's `value`). `strictRequired` stays at Ajv's default, off: Ajv compiles `if`/`then`, `anyOf` and `oneOf` before the `properties` beside them, so it flags 36 of AEE's conditional `required` keys, though each names a property the schema declares. A new test compiles every schema, and another checks that strict mode rejects a missing type, an unknown keyword and an unknown format. `@aee/schemas` exports `createSchemaAjv()`, the Ajv instance it validates with. The schemas accept and reject the same data as before.
- The test lab checks each page's heading outline as a screen reader lists it, from the accessibility tree, instead of by tag name (audit B3). The old check listed the `<h1>`–`<h6>` tags, so it would have missed a `<div role="heading" aria-level="2">` and counted an `<h2>` hidden with `aria-hidden` or one with `role="presentation"`; a new test with each of these failed on it. It now uses Playwright's `getByRole("heading")`, checks each heading's level with an aria snapshot and its exact accessible name with `toHaveAccessibleName`. `site/test-lab-contract.json` gives each heading's level and name (`headingOutline: [{ "level": 1, "name": "Workspace overview" }, …]`) instead of tag names, so a renamed or emptied heading also fails. The lab pages are unchanged.
- axe-core and `@axe-core/playwright` move together to 4.14.0. axe 4.14 makes `label-content-name-mismatch` a default WCAG 2.1 A rule instead of an experimental one, so it still runs and blocks release; AEE now switches on four experimental WCAG rules (`css-orientation-lock`, `p-as-heading`, `table-fake-caption`, `td-has-header`). Rule links point at Deque's 4.14 pages.

- A click or submit no longer passes the change-response judge just because it moved focus onto the clicked control. A click focuses what it lands on by itself (HTML's focusing steps), so clicking a button that does nothing passed with "focus moved". It now fails when nothing else in the accessibility tree changed, or is `unknown` when something unrelated did, as for any press with no response of its own. Chrome moving focus to the page when a click lands on something that cannot take focus is not counted either. Focus moving anywhere else, such as into a dialog the click opened, still counts. The judgment says when it set the click's own focus aside, and a failure lists the focus records as evidence. Enter and Space are unchanged: focus is already on the control. Change-response judge 0.3.0.
- AEE needs Node 22.18 or later on Node 22, or 24.11 or later on Node 24 (`^22.18.0 || >=24.11.0`), up from 22.13. `aee fix` reads source files with `@babel/parser`, which moves to 8.0.7, and Babel 8 supports only that range. CI's oldest-Node job now runs exactly 22.18.

- The keyboard and change-response judges decide whether a press responded from what a keyboard or screen-reader user perceives, not from whether the page's HTML changed. A press responds when the pressed control's state in Chrome's accessibility tree changes (checked, expanded, pressed, selected, value, name), when something it names with `aria-controls` does, when focus moves, when Guidepup's virtual screen reader announces a live-region update (a status message, WCAG 4.1.3), or when the network is used. Space on a native checkbox, which ticks it without changing the HTML, failed before and passes now. A dead button on a page where something else changes, such as a clock, passed before and is now `unknown`, with what changed named. A button whose only effect is to change text that is not a live region is `unknown` too: a sighted user sees it, a screen-reader user is not told. The markup diff stays in the record as supporting evidence. Failing a press now needs the accessibility-tree observer; without it the judges return `unknown`. The keyboard lane of `runInputComparison` listens with Guidepup's reader through every press. Keyboard judge 0.3.0, change-response judge 0.2.0.
- A live region that announces on its own, such as a clock or a ticker, no longer makes a dead button pass. While the virtual reader listens, the run now leaves the page untouched for 1.5 seconds before each press (`policy.capture.watchWithoutInputMs`) and records what the page announced and what changed in Chrome's accessibility tree in that time. An announcement after the press is not counted when it came from a live region that was already announcing on its own, or when Chrome's tree cannot say which region it came from and the page was announcing on its own; the judges return `unknown` and name the announcement. A status message from another region still counts while a clock ticks. Guidepup's reader does not say which region spoke, so each announcement is placed in the changed live region whose name or text holds its words, the region being the nearest node Chrome gives a `live` property. New evidence: the reader's "before" record lists `liveRegionAnnouncementsWithoutInput`, the accessibility tree's "before" record `accessibilityChangesWithoutInput`, and each comparison the `liveRegions` its changes are in, all checked by `evidence-record.schema.json`. Announcements the reader heard after it began listening but before the press no longer count as the press's response either. A region that announces less often than the watch lasts still goes unnoticed. Virtual-screen-reader observer 0.3.0.

- The virtual screen reader speaks through [Guidepup's virtual screen reader](https://github.com/guidepup/virtual-screen-reader) (pinned to 0.32.1) instead of AEE's own rules. 0.33.0 is skipped: its `start()` sets up a user-event session in the page that can break later typing in a React input ([guidepup/virtual-screen-reader#250](https://github.com/guidepup/virtual-screen-reader/issues/250)), and AEE reads a test's own page. It announces every state and property Guidepup knows, which AEE's own reader did not: invalid, read-only and a field's value, its description and error message, a placeholder, a popup, a slider's or progress bar's value, a list item's or tab's position, a sort order, "current page", a modal dialog, and where each element ends. Announcements change wording ("heading, Invoices, level 1" for "Invoices, heading, level 1"), and transcripts are `engineVersion` 0.2.0 with a `speechEngine` field. Each step still names its element, position and Chromium role, and the screen-reader judge leaves a step undecided when Guidepup and Chromium disagree on the element's name. Guidepup is loaded as a plain script over the DevTools protocol, the way `@axe-core/playwright` loads axe, so a page's Content-Security-Policy does not refuse it. Two known differences from screen readers, reported to Guidepup: it announces an unnamed form ([guidepup/virtual-screen-reader#253](https://github.com/guidepup/virtual-screen-reader/issues/253)), and reads the hidden content of a closed `<details>` ([#254](https://github.com/guidepup/virtual-screen-reader/issues/254)).
- `npm run readers:compare` lines the two transcripts up both ways with [jsdiff](https://github.com/kpdecker/jsdiff) and lists what each reader said that the other did not, word for word, instead of a "Says what VoiceOver says" percentage. That score left out every role and state word, so "not checked" against "checked", "button" against "link" and a control with no name all counted as heard or were left out; every word now counts, and only the order of words within a phrase does not. The comparison also says why the real reader's walk ended, including when it reached the step limit and may not have read the whole page. Each real-reader step waits until the reader has finished speaking, so a slow reader no longer ends the walk halfway, and VoiceOver's usage hints are cut from what it said.
- `npm run readers:compare` compares the real screen reader with AEE's own virtual reader, not screen-reader-cli's, and drives VoiceOver, NVDA or Orca through Guidepup's Playwright integration. It now works on macOS 27. Where the real reader cannot start, the command fails with Guidepup's reason instead of writing a one-sided comparison.
- The homepage's screen-reader video is AEE's own virtual reader reading the demo page.
- Each virtual-reader step's DOM focus (`domFocusBefore`, `domFocusAfter`) names the focused element in whichever frame holds it, including a cross-site frame Chrome renders in another process, instead of the `<iframe>` element the top document reports. Focus is followed through each document's `activeElement`, into each shadow root's, and into the frame's own document through that frame's DevTools session. Each is now an object, `{ nodePath, backendDOMNodeId, frameId, framePath }`, named as the step's item is, and the text transcript writes it as `#cross >>> html > body > button`. `focusMoved` is true when focus moves between two controls inside one frame, which was reported as no move.
- The focus observer's DOM focus follows focus into a cross-site frame Chrome renders in another process, through that frame's DevTools session, the same walk the virtual reader's DOM focus uses. Before, the chain stopped at the `<iframe>` (a cross-site frame's `contentDocument` is null to the page), so the deepest active element, its focus-visible style, role, name and `aria-activedescendant` described the frame element, not the focused control. Each element is now described in its own document, and the elements of the chain carry `frameId` and, inside a frame, `framePath`; the element with focus in each document carries `backendDOMNodeId`, so the deepest element joins to `accessibilityFocus` and to its frame's accessibility tree. An `aria-activedescendant` or dialog `aria-labelledby` reference is looked up in the element's own document or shadow root, not the top document.
- The focus observer records each focused element's place in the page's tab order, counted across the top document and every frame, same-origin and cross-site, so the keyboard judge can tell whether Tab or Shift+Tab moved focus forward or backward when focus enters, leaves or moves inside a frame. `focusOrderIndex` and `focusableCount` keep their names and now mean the page-wide place and count. Before, they counted the top document's light-DOM tab stops with AEE's own selector, so a control inside a frame or a shadow root had no place and the judge passed every such step at 0.75 with the direction unchecked, and an element with a positive `tabindex` was counted in document order rather than where Tab reaches it. Each document's tab stops now come from [tabbable](https://github.com/focus-trap/tabbable) 6.5.0 (focus-trap's library, pinned), which orders them by HTML's sequential focus navigation, enters open shadow roots, and handles radio groups, `inert`, disabled fieldsets and closed `<details>`. tabbable leaves frames out, so each frame's tab stops are placed at its `<iframe>` element's place by tabbable's own sorting rule, read through the frame's own DevTools session; an `<iframe>` with a tabindex, which tabbable lists itself, is entered where tabbable lists it. Chrome's own Tab walk was the check: a frame with `tabindex="-1"`, hidden, or under an `inert` shadow host is skipped, a positive tabindex on the `<iframe>` sorts its frame, a frame slotted into a shadow root comes after that root's positive tabindex, and a frame with nothing to focus is one stop itself (the innermost one when frames nest). When any frame cannot be read or placed, or is held by an element other than `<iframe>`, no place is recorded and the judge says the direction is unverified, since a missing frame would shift every later place; the rest of the focus record is kept. The keyboard and change-response judges now tell two focused elements apart by frame and node as well, so a Tab between two like-named buttons, in two frames or in one, counts as a move rather than a stall. The build script that bundles Guidepup for the page, now `scripts/build-page-scripts.mjs`, bundles tabbable the same way, and both load into each frame through one helper.
- The page's tab order includes the tab stops inside closed shadow roots (`attachShadow({ mode: "closed" })`), and places a frame inside one. Before, a frame in a closed root made the whole order unknown, so no Tab on such a page had a place, and focus on a control in a closed root was recorded as its host (`vault-panel`, with no name or role), since a page cannot reach into a closed root. The closed roots are now read over the DevTools protocol, by walking each process's DOM through every shadow root (`DOM.describeNode` with `pierce`), and handed to tabbable as the function its README documents for closed roots (`getShadowRoot`). Focus is followed into them too, so the focus observer names the control that has focus, its role, name and focus style, and the virtual reader's `domFocusBefore` and `domFocusAfter` name it as well. A frame slotted into a closed root is placed at its slot. The check was Chrome's own Tab walk: a closed root's positive tabindex first, then its button, the cross-site frame it holds, and the frame slotted into it, each recorded where Chrome's Tab lands. The walk costs about 4 ms per 1,000 elements in Chrome; a whole focus capture measured 13 ms against 8 ms on a page of 900 elements, 61 against 21 ms at 9,000 and 457 against 97 ms at 45,000, paid before and after each step. It reads the DOM 100 levels at a time, since Chrome refuses one reply nested 150 levels deep.
- The keyboard, change-response and focus-management judges treat focus that falls to a document's `<body>` as lost focus (audit item A4). When no element has focus, the browser names `<body>` as the active element, and the judges only treated an empty record as lost, so a Tab onto a button a script blurs passed as "Keyboard focus advanced forward … to body", Enter on a button that dropped focus counted "focus moved" as its response, and a click whose only effect was to drop focus passed. Each now fails, and every summary says "body (no element has focus)". Two kinds of `<body>` are not lost, and Chrome's own Tab was the check for both: a frame with nothing to focus, which Tab stops on and whose `<body>` is then active, carries a place in the tab order and passes; and Tab from the last tab stop (Shift+Tab from the first) moves focus to the browser's own controls, which the focus record now shows as `documentHasFocus: false` (the top document's `document.hasFocus()`), and passes at 0.95 instead of 0.75. Leaving the page from any other tab stop is `unknown`. So that a `<body>` with no place is known not to be a tab stop, `focusableCount` is now recorded on every element whenever the page's tab order was counted, not only beside a place; when it could not be counted (an unreadable frame) a frame's `<body>` is `unknown` rather than called lost. A Tab that moves against the predicted tab order is now `unknown`, not a failure, with both places named, as the audit advised: the browser's Tab is what a keyboard user gets, and the prediction can be wrong. Chrome puts a popover's content right after the control that opened it while tabbable keeps document order, so Tab out of an open popover was reported as wrong direction. `focus-state.schema.json` requires `documentHasFocus`. Keyboard judge 0.4.0, change-response judge 0.4.0.

### Added

- axe's experimental rules filed under a WCAG A/AA criterion now run, and their failures block release like any other WCAG rule. In axe 4.13 these are `p-as-heading` (text styled as a heading that is not one), `td-has-header` (data cells with no header), `table-fake-caption` (a table row used as its caption), `label-content-name-mismatch` (a control's visible text missing from its accessible name) and `css-orientation-lock` (content locked to portrait or landscape). axe switches them off by default; AEE enables them by id from axe's own rule list, so a rule axe adds or graduates is picked up. `css-orientation-lock` needs a stylesheet to read, so on a page with none at all it needs review. The axe record's `ruleSelection` names them as `experimentalTags`.
